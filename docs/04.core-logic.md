# Core Logic
This section describes the core functional logic implemented by the platform, allowing a clear understanding of how the platform functions.

## USSD code Request

A USSD Code request starts when a user dials a code on their mobile device.

As the USSD Code request comes from a Mobile Network Operator (MNO) USSD Gateway into the platform, it checks whether the request is valid and then checks which application Entry point is mapped to the short code. If there is no mapped application entry point, it outputs a Entry point not found message.

If there is a mapped application entry point but there is an active suspension, then the defined suspension message is returned.

If there is no active suspension and there is a short list bound to the entry point, then the platform checks whether the requester MSISDN is in the short list. If the MSISDN is not in the short list then it outputs the exclusion message.

If there is no active suspension and there is no short list bound to the entry point or if the requester MSISDN is in the short list, then the platform initializes session and then proceeds with Backend dispatching.


### Session initialization

Session initialization is about creating a new session for a USSD request. It involves setting up the initial state of the session, including the session ID, the request ID, and the request parameters.

The initialization of a session involves setting session values that have been predefined on the Entry-point level.


### Backend dispatching
Backend dispatching is about interacting with a USSD Application backend to process a USSD Request.

The platform first checks if it has a valid Application map in its cache. If it does not, it attempts to fetch the Appication map from the backend, by issuing a request to the backend.

If the Application map cannot be fetched or cached, the platform outputs the internal error message.

If the Application map is successfully fetched and cached, the platform proceeds with Backend disptaching.

Backend dispatching is essentially about contacting the backend to retrieve content and process user input.
There two kinds of requests that the platform sends to the backend for this purpose:

* Get Initial Content - Request to obtain the content corresponding to a specific activity. 
* Process User Input - Request to process input data that has been collected in the context of an activity.

Any error found during backend dispatching is considered an application error and the platform short circuits and returns an error message to the end user.

Whenever the Entry-Point has more than one Backend, the platform will first check the backend that has a whitelist attached to it and only if the user is part of that Shortlist will the platform send the request to that backend, otherwise it sends the request to the backend without a Short list bound to it.


## Screen/App navigation flow
The navigation on a USSD application flows from one activity to the other according to 2 things:

* User input
* Backend response

The platform first sends a "Get Initial Content" request to the backend, addressing the initial activity.
The backend responds a "Get Initial Content" request with:

* The screen content to be displayed
* Indication of whether content expects input or not
* The session values to be updated (optional)
* A Input Traps Map (optional)

The platform delivers the content to the Mobile network which then delivers to the Mobile phone which displays it and collects the user input.

The platform will act in one of two ways depending on whether the backend responded with an Input Traps Map or not.

If the backend responded with an Input Traps map and the user input matches any of the traps then the platform sends a "Get Initial Content" to the backend addressing the Activity defined on the trap.

If the backend did not define an Input Traps Map or the input value did not match any of the traps then the platform sends a "Process User Input" request to the backend addressing the current activity.  The backend can only respond a "Process User Input" request with:

* The screen content to be displayed (optional)
* The session values to be updated (optional)
* The ID of the next activity (optional)

The backend MUST choose between returning the screen content and the ID of the next activity. The next activity ID must be different from the current Activity ID, if not then the platform responds the end user with an error message and crashes the session. 

If the Backend responds with the ID of the next Activity then the platform will issue a "Get Initial Content" request to the backend addressing that activity and then the cycle continues.

Both the "Get Initial Content" and "Process User Input" requests carry the session values that have been defined as requirements for the activities they are addressing.



## Template processing
The platform has the capability of pre-processing the screen content returned by the backend before its delivered to the Mobile network. The backend just needs to state that the content it's returning is a template and not the final content. The platform will pre-process it using Handlebars template engine, ensuring that the session values defined for that activity are available for interpolation. The main value of template processing is to enable the platform to cache dynamic content. Without template processing the platform woudn't be able to cache dynamic content, missing out on most of the activities that generate dynamic content, where dynamic content is basically content that varies according to the session values. Template processing is most valuable when it enables the platform to serve a screen without any backend call at all. If the backend still has to be invoked to get fresh data, templating doesn't help at all. 

The processed template is never cached, only the template itself is cached.


## Content trimming
The platform enforces USSD Content limit by truncating any characters after the last visible/displayable character.

## USSD Redirection
A USSD Redirect is a mechanism that allows a user to be redirected from current journey/flow to another.
The platform allows redirect to Internal destinations (Application Entry points) or External ones (Known by the USSD Gateway).

The Redirect is triggered by the Backend response, which includes the destination to redirect the user to.
The Backend responds with HTTP 307, with location header containing the destination.

A redirect causes the same request that was received to be sent to the redirect destination.
There is a redirect depth limit of 3 and redirects to the same destination are not allowed, causing an immediate error.

### Redirecting within the platform
Redirecting within the platform is achieved by sending a HTTP 307 response with the location header containing the destination. There two internal redirect types: Entry-Point level redirect and Activity redirect.

Internal redirects cause the platform to resend the request to the redirect destination.

#### Entry-point redirect
```
HTTP/1.1 307 Temporary Redirect
Location: /
Redirect-Type: EntryPoint
Entry-point: {entry-point-id}
```

#### Activity redirect
Internal redirect also supports redirecting to another activity:

```
HTTP/1.1 307 Temporary Redirect
Location: /
Redirect-Type: Activity
Activity: {activity-id}
```


### Redirecting to external Application
A redirect to an external application requires the short code of the application.
```
HTTP/1.1 307 Temporary Redirect
Location: /
Redirect-Type: Gateway
Short-Code: {short-code}
```

An external redirect is handled by interacting with the edge-server which talks to the MNO.

## Session resuming
Whenever the platform sends a the first Get Initial Content request of a session it sends a flag that indicates whether the previous session is resumable or not, allowing the Backend to respond with "resumeSession=true", which will cause the Platform to load all values from last session as long as the session status is one of: Cancelled, Active, Crashed, Expired. A resumed session will have a "resumed=true" session value set. A session with age higher than 120 seconds is not resumable. The 120 seconds is counted from the last update done to the session.
