# Event Dispatcher

## Overview

The **Event Dispatcher** is the platform's event distribution service. It consumes events produced by the core-engine and delivers them to configured upstream consumers — monitoring backends, SIEM systems, webhook endpoints, and any other destination that needs visibility into platform activity.

The core-engine never calls the Event Dispatcher directly. Events flow through a **NATS JetStream** channel, decoupling production from delivery. The Event Dispatcher's availability has no impact on USSD request processing.

---

## Responsibilities

- Consume events from NATS JetStream
- Deliver each event to all configured upstream destinations
- Acknowledge messages to NATS only after successful delivery
- Deduplicate redelivered messages using the event `eventId`
- Emit its own operational metrics for observability

---

## Transport

### Inbound (from core-engine)

The Event Dispatcher subscribes to a NATS JetStream stream. The core-engine publishes all events to this stream via the outbox mechanism described in the [Core Engine Event Dispatcher Contract](02.core-engine.md#event-dispatcher-contract).

NATS JetStream retains messages on the stream until the Event Dispatcher acknowledges them. If the Event Dispatcher is unavailable, messages accumulate on the stream and are delivered once it reconnects — no events are lost provided the stream retention limit is not exceeded.

**Deduplication:** Because the outbox pattern guarantees at-least-once publish, the Event Dispatcher may receive the same event more than once (e.g. if the core-engine goroutine crashed after publishing but before deleting the outbox row). The Event Dispatcher deduplicates using the `eventId` field in the event envelope before forwarding to upstream destinations.

### Outbound (to upstream consumers)

Each upstream destination is configured independently. The Event Dispatcher fans out every event to all matching destinations in parallel. A delivery failure to one destination does not affect delivery to others.

Supported destination types:

| Type | Description |
|---|---|
| **Webhook** | HTTP POST to a configured URL with the event envelope as the JSON body |
| **OpenTelemetry Logs** | Emit the event as a structured OTel log record to an OTLP-compatible collector |
| **NATS subject** | Re-publish to a secondary NATS subject or stream (e.g. for downstream consumers in the same organisation) |

Additional destination types may be introduced without changes to the core-engine or the NATS contract.

## Event Envelope

Every event arriving from NATS carries the common envelope defined by the core-engine:

| Field | Type | Description |
|---|---|---|
| `eventId` | string (UUID) | Unique identifier for this event instance. Used for deduplication. |
| `eventType` | string | Dot-separated event type identifier (e.g. `session.started`, `audit_log.written`) |
| `occurredAt` | string (ISO 8601) | Timestamp when the event occurred in the core-engine |
| `spaceId` | string | ID of the space the event belongs to. Empty for platform-scoped events. |
| `payload` | object | Event-specific fields — see the [Core Engine Events catalogue](02.core-engine.md#events) |

## Destination Configuration

Destinations are defined in the Event Dispatcher configuration file. Each destination entry specifies a type, connection parameters, and an optional event type filter.

```yaml
event_dispatcher:
  destinations:
    - name: siem-webhook
      type: webhook
      url: "https://siem.example.com/ingest"
      headers:
        Authorization: "Bearer <token>"
      filter:
        eventTypes:
          - "audit_log.written"
          - "audit_log.cleanup_executed"

    - name: otel-collector
      type: otel_logs
      endpoint: "http://otel-collector:4318"
      filter:
        eventTypes: []   # empty = all event types

    - name: analytics-stream
      type: nats
      subject: "cardinal.events.analytics"
      filter:
        eventTypes:
          - "session.started"
          - "session.ended"
          - "request.processed"
```

**Filter behaviour:** When `eventTypes` is non-empty, only events whose `eventType` matches an entry in the list are delivered to that destination. An empty or absent `eventTypes` list means all event types are delivered.

## Delivery Guarantees

| Concern | Behaviour |
|---|---|
| **At-least-once delivery** | NATS redelivers unacknowledged messages. The Event Dispatcher acknowledges only after all configured destinations have accepted the event. |
| **Deduplication** | The Event Dispatcher tracks recently seen `eventId` values and discards duplicates before forwarding. |
| **Partial destination failure** | If delivery to one destination fails after the retry budget is exhausted, the event is acknowledged to NATS (to avoid indefinite redelivery) and the failure is recorded in the dispatcher's error log and metrics. Delivery to other destinations is unaffected. |
| **Destination unavailability** | Each destination has a configurable retry policy (attempts, backoff). Transient failures are retried within the budget before the event is considered undeliverable. |

## Operational Metrics

The Event Dispatcher exposes the following metrics:

| Metric | Type | Description | Dimensions |
|---|---|---|---|
| `dispatcher_events_consumed_total` | Counter | Total events consumed from NATS | `event_type` |
| `dispatcher_events_delivered_total` | Counter | Successful deliveries to upstream destinations | `destination`, `event_type` |
| `dispatcher_events_failed_total` | Counter | Events that exhausted the retry budget for a destination | `destination`, `event_type` |
| `dispatcher_events_deduplicated_total` | Counter | Events discarded as duplicates | `event_type` |
| `dispatcher_delivery_duration_seconds` | Histogram | Delivery latency per destination | `destination` |
| `dispatcher_nats_lag` | Gauge | Number of unacknowledged messages on the NATS stream | — |
