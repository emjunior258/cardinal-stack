# Edge Server

## Overview

The **edge-server** is the network boundary of the cardinal-stack. It is the component that Mobile Network Operator (MNO) USSD Gateways talk to, and through which all inbound USSD traffic enters the platform. It is equally the component through which USSD Push requests leave the platform toward MNO gateways.

The edge-server has no knowledge of application logic, tenants, sessions, or business rules. Its sole concern is protocol translation: converting MNO-specific wire formats into the platform's internal representation and back, and routing traffic to and from the core-engine.

The edge-server is implemented in **Go**. MNO plugins are **Go plugins** — shared libraries (`.so` files) compiled independently from the edge-server using the **Cardinal Edge SDK**. Plugins are loaded at runtime from the filesystem, making it possible to add or update operator support without recompiling the edge-server itself.

---

## Responsibilities

- Receive inbound USSD requests from MNO gateways and authenticate them.
- Parse and validate MNO-specific payloads.
- Normalize validated requests into the platform's internal `UssdRequest` format.
- Forward normalized requests to the core-engine and relay the response back to the MNO gateway in its expected format.
- Expose a **USSD Send API** for the core-engine to initiate USSD Push sessions via any MNO.
- Expose a **Simulation API** that emulates the full MNO-gateway interaction for development and testing, without involving a real mobile network.

---

## Design Principles

**Stateless.** The edge-server holds no session state and no business state. Every request is handled independently. This makes it trivially horizontally scalable and keeps failure domains small.

**MNO-agnostic core, MNO-specific plugins.** All operator-specific logic is encapsulated inside discrete plugins. The edge-server's routing, normalization pipeline, and API surfaces are protocol-neutral.

**Fail-fast at the boundary.** Requests that cannot be authenticated, parsed, or mapped to a known network are rejected immediately at the edge. Invalid traffic never reaches the core-engine.

**Minimal coupling to the core-engine.** The edge-server communicates with the core-engine over a single well-defined HTTP interface. It is unaware of tenants, applications, or entry points.

## MNO Plugin Model

Each MNO supported by the platform is encapsulated in a plugin. A plugin is a **Go plugin** (compiled with `go build -buildmode=plugin`) that produces a `.so` shared library. Plugins are developed independently using the **Cardinal Edge SDK** — a Go module that defines the plugin interface and all shared types. The edge-server loads plugins at runtime from the filesystem; no plugin participates in request handling unless it is explicitly listed in configuration.

### Cardinal Edge SDK

The SDK is a standalone Go module (`github.com/cardinal-stack/edge-sdk`) that serves as the shared contract between the edge-server and all plugins. It exposes:

- The `Plugin` interface that all plugins must implement.
- The `EdgeSDK` interface that the edge-server implements and passes to each plugin at initialization, giving plugins a way to submit parsed USSD requests back into the platform.
- The `Capabilities`, `UssdRequest`, `UssdResponse`, and `PushCommand` types.
- Any shared utilities useful to plugin authors (e.g. structured error types, logging helpers).

A plugin author imports only the SDK — not the edge-server itself. The edge-server equally imports only the SDK to know the interface it expects to find when it opens a `.so` file.

#### `EdgeSDK` interface

The `EdgeSDK` interface is the API through which a plugin hands a parsed inbound request to the edge-server and receives the response synchronously:

```go
type EdgeSDK interface {
    // SubmitRequest hands a normalized UssdRequest to the edge-server for processing.
    // Blocks until the core-engine responds. The plugin uses the returned UssdResponse
    // to compose its MNO-specific reply.
    SubmitRequest(ctx context.Context, req UssdRequest) (UssdResponse, error)
}
```

This call crosses from the plugin's own goroutine into the edge-server's processing pipeline. The plugin is responsible for translating the returned `UssdResponse` (or error) into the MNO-specific HTTP response it sends back to the gateway.

> **Compatibility note:** Go plugins require that the plugin and the host binary are built with the same Go version and compatible module dependency graphs. The SDK version used to build a plugin must match the version the edge-server was built against. The edge-server must log the SDK version it was built with on startup and reject plugins built against an incompatible SDK version.

### Plugin Contract

Every MNO plugin must implement the following operations, expressed as a Go interface:

**1. Capabilities**

Returns a `Capabilities` struct that declares what the plugin supports. The edge-server reads this at startup to know which operations are valid for each network. Currently declared capabilities:

| Capability | Description |
|---|---|
| `ReceivesUssd` | Plugin can receive and parse inbound USSD requests from an MNO gateway. All plugins must declare this. |
| `SendsPush` | Plugin can initiate USSD Push sessions toward an MNO gateway. Optional — not all MNOs support push. |

**2. Initialize**

Called once at startup with the path to the plugin's configuration file and an `EdgeSDK` instance. The plugin loads and validates its own configuration and stores the `EdgeSDK` reference for use during request handling. If initialization fails, the edge-server must refuse to start.

**3. Start**

Called by the edge-server after all plugins have been successfully initialized. The plugin starts its own HTTP server (or equivalent listener) on whatever port and protocol the MNO requires. The plugin is fully responsible for the lifecycle of this server — binding, TLS, authentication, request parsing, and response serialization are all internal to the plugin. When a request arrives, the plugin parses it and calls `EdgeSDK.SubmitRequest` to hand the normalized `UssdRequest` to the edge-server, then uses the returned `UssdResponse` to compose the MNO-specific reply.

**4. Stop**

Called by the edge-server during graceful shutdown. The plugin must stop its HTTP server and release all resources.

**5. Initiate push**

_Required only if the plugin declares the `SendsPush` capability._

Called by the edge-server via a native Go call when the core-engine requests a USSD Push. Accepts a `PushCommand` and performs the MNO-specific HTTP call (or equivalent) to initiate the push session. Returns a `PushResult` containing the session ID assigned by the MNO gateway, or an error including the raw failure from the MNO gateway when available. The session ID is forwarded by the edge-server to the core-engine so the session can be correlated with subsequent inbound requests.

### Plugin Configuration

Each plugin defines its own configuration schema and is responsible for parsing it. The edge-server passes the path of the plugin's configuration file to the `Initialize` operation at startup. Configuration files can be in any format the plugin chooses (YAML is recommended for consistency).

Plugin configuration typically includes: MNO gateway URL, authentication credentials, timeouts, and any MNO-specific parameters required to interact with the operator.

### Plugin Registration

Plugins are registered in the edge-server configuration file. The edge-server scans the configured plugins directory for `.so` files and loads only those explicitly listed in configuration — files present in the directory but not listed are ignored.

Each entry in the plugin list must specify:

- The **filename** — the `.so` filename within the plugins directory (e.g. `mno-a.so`).
- The **network ID** — the platform network identifier this plugin instance is bound to. Must be unique across all registered plugins.
- The **configuration file path** — absolute or relative path to the plugin's own configuration file.

Each plugin entry maps to exactly one network ID. The same `.so` file can be listed more than once with different network IDs and different configuration files, enabling a single plugin implementation to serve multiple operator contracts.

When the core-engine requests a push for a network ID with no registered plugin, the edge-server returns HTTP `404` to the core-engine and records an `edge_request_errors_total` metric with `error_type=plugin_not_found`.

## Internal Data Model

These are the structures that flow across the boundary between the edge-server and the core-engine.

### `UssdRequest`

| Field | Type | Description |
|---|---|---|
| `requestId` | string (UUID) | Unique identifier assigned by the edge-server for this request |
| `sessionId` | string | Session identifier as provided by the MNO gateway |
| `network` | string | Platform network identifier (e.g. `mno-a`) |
| `msisdn` | string | MSISDN of the end user |
| `code` | string | (optional) The full USSD code dialed by the user, including the short code and any additional parameters (e.g. `*123*01*1000#`) |
| `input` | string | (optional) User input string |
| `sessionType` | enum | `dial` or `push` |
| `location.mcc` | string | (optional) Mobile Country Code of the cell the subscriber is connected to |
| `location.mnc` | string | (optional) Mobile Network Code of the cell the subscriber is connected to |
| `location.lac` | string | (optional) Location Area Code of the cell the subscriber is connected to |
| `location.cid` | string | (optional) Cell ID of the cell the subscriber is connected to |

### `UssdResponse`

| Field | Type | Description |
|---|---|---|
| `content` | string | Screen content to display to the user |
| `requireInput` | boolean | `true` if the session is awaiting input from the user; `false` if the session has terminated |

### `PushCommand`

| Field | Type | Description |
|---|---|---|
| `network` | string | Target MNO network identifier |
| `msisdn` | string | MSISDN of the target subscriber |
| `entryPointId` | string | ID of the Push entry point to initiate the session on |
| `sessionValues` | map[string]string | Optional key-value pairs used to initialize the session state before the first request is processed |
| `correlationId` | string | Identifier propagated for tracing the push end-to-end |

### `PushResult`

Returned by the plugin's `InitiatePush` operation and forwarded by the edge-server to the core-engine in the USSD Send API response.

| Field | Type | Description |
|---|---|---|
| `sessionId` | string | Session identifier assigned by the MNO gateway upon accepting the push request |

## Exposed APIs

### Inbound MNO Traffic

The edge-server exposes no inbound endpoint for MNO traffic. Each plugin starts and owns its own HTTP server on a port and protocol dictated by the MNO's integration requirements. MNO gateways connect directly to the plugin's server.

When an inbound request arrives, the plugin is solely responsible for:
- Authenticating the request.
- Parsing the MNO-specific payload.
- Calling `EdgeSDK.SubmitRequest` with the normalized `UssdRequest` to hand off to the edge-server.
- Receiving the `UssdResponse` back from `SubmitRequest` and serializing it into the MNO-specific reply.
- Writing the HTTP response back to the MNO gateway.

The plugin's listening port and any authentication parameters are defined in the plugin's own configuration file.

### USSD Send API

The core-engine calls this API to trigger a USSD Push via a registered MNO plugin. The path mirrors the inbound convention — the `network-id` segment identifies which plugin handles the outbound push.

```
POST /mno/{network-id}/push
```

**Request body:**

```json
{
  "msisdn": "+2547XXXXXXXX",
  "entryPointId": "transfer-push",
  "sessionValues": {
    "transferAmount": "1000",
    "targetAccount": "254700000000"
  },
  "correlationId": "uuid"
}
```

The `network-id` in the path is sufficient to resolve the target plugin; it does not need to be repeated in the body. `sessionValues` is optional and may be omitted when no pre-initialized session state is needed.

**Response body (`202 Accepted`):**

```json
{
  "sessionId": "mno-assigned-session-id"
}
```

The `sessionId` is the identifier assigned by the MNO gateway and must be used by the core-engine to correlate subsequent inbound requests from the subscriber back to this session.

**Responses:**

| Status | Meaning |
|---|---|
| `202 Accepted` | Push accepted by the MNO gateway; response body contains the MNO session ID |
| `400 Bad Request` | Missing or invalid fields |
| `404 Not Found` | No plugin registered for the specified `network-id` |
| `501 Not Implemented` | Plugin is registered for the network but does not declare the `SendsPush` capability |
| `502 Bad Gateway` | MNO gateway returned an error or was unreachable |

This endpoint is internal and must not be exposed outside the platform network.

### Simulation API

The Simulation API allows a full USSD session to be exercised without a real MNO gateway. It is the integration point for the Emulator app and for automated tests.

The API is built around the concept of a **Virtual Device** — a simulated mobile handset bound to a real network and MSISDN. Once registered, a virtual device is used to send USSD requests and to receive USSD Push deliveries. Virtual devices take precedence over MNO plugins: the edge-server routes traffic for a registered MSISDN to its virtual device for both inbound requests and push delivery, bypassing the MNO plugin entirely.

#### Register a Virtual Device

```
POST /simulate/devices
```

**Request body:**

```json
{
  "network": "mno-a",
  "msisdn": "+2547XXXXXXXX",
  "imei": "356938035643809",
  "callbackUrl": "http://emulator:9090/push"
}
```

| Field | Description |
|---|---|
| `network` | Platform network identifier the device belongs to |
| `msisdn` | MSISDN of the simulated subscriber |
| `imei` | IMEI of the simulated device |
| `callbackUrl` | URL where the edge-server will deliver USSD Push requests destined for this device |

**Response (`201 Created`):**

```json
{
  "deviceId": "vdev-uuid"
}
```

The returned `deviceId` must be used in all subsequent USSD requests and is the key used to look up the device for push delivery. A virtual device registration is valid for the lifetime of the edge-server process unless explicitly deregistered.

#### Deregister a Virtual Device

```
DELETE /simulate/devices/{deviceId}
```

Returns `204 No Content` on success. After deregistration, traffic for the device's MSISDN is routed to the MNO plugin as normal.

#### Send a USSD Request

```
POST /simulate/ussd
```

**Request body:**

```json
{
  "deviceId": "vdev-uuid",
  "sessionId": "sim-session-001",
  "sessionType": "dial",
  "code": "*123*01*1000#",
  "input": "1"
}
```

| Field | Description |
|---|---|
| `deviceId` | ID of the registered virtual device making the request |
| `sessionId` | Session identifier for this interaction |
| `sessionType` | `dial` or `push` |
| `code` | (optional) The full USSD code dialed |
| `input` | (optional) User input for the current session step |

The edge-server resolves the network and MSISDN from the registered virtual device, constructs the `UssdRequest`, and forwards it to the core-engine through the same pipeline as real traffic.

**Response body** mirrors `UssdResponse`:

```json
{
  "content": "Welcome\n1. Option A\n2. Option B",
  "requireInput": true
}
```

#### Push Delivery to a Virtual Device

When a USSD Push is initiated for an MSISDN that has a registered virtual device, the edge-server handles the push internally rather than invoking the MNO plugin. It generates a session ID, constructs the initial `UssdRequest`, and submits it to the core-engine to obtain the first `UssdResponse`. That response is then delivered to the virtual device's `callbackUrl` as an HTTP POST:

```
POST {callbackUrl}
```

**Request body:**

```json
{
  "deviceId": "vdev-uuid",
  "sessionId": "sim-generated-session-id",
  "content": "You have a pending transfer. Reply 1 to confirm.",
  "requireInput": true
}
```

| Field | Description |
|---|---|
| `deviceId` | ID of the virtual device the push is addressed to |
| `sessionId` | Session identifier generated by the edge-server for this push session |
| `content` | Screen content returned by the core-engine for the initial activity |
| `requireInput` | `true` if the session is awaiting input; `false` if the session has terminated |

The virtual device is expected to respond with `200 OK`. The `sessionId` must be used in all subsequent USSD requests from the virtual device for this session.

## Request Flow

### Inbound: MNO Gateway → Core Engine

```
MNO Gateway
   │
   │  HTTP (MNO-specific protocol & port)
   ▼
Plugin HTTP Server  (own port, owned entirely by the plugin)
   ├─ Authenticate request
   ├─ Parse payload → UssdRequest
   │
   │  EdgeSDK.SubmitRequest(UssdRequest)  [native Go call into edge-server]
   ▼
Edge Server
   ├─ Assign requestId
   │
   │  HTTP POST /ussd  (UssdRequest)
   ▼
Core Engine
   │
   │  HTTP 200 (UssdResponse)
   ▼
Edge Server
   │
   │  returns UssdResponse  [SubmitRequest call returns to plugin]
   ▼
Plugin HTTP Server
   ├─ Serialize UssdResponse → MNO-specific format
   │
   │  HTTP response (MNO-specific format)
   ▼
MNO Gateway
```

Errors from the core-engine are surfaced to the plugin as an error return from `SubmitRequest`. The plugin is responsible for translating them into the appropriate MNO-specific error response; internal error details must never be forwarded to the MNO gateway.

### Outbound: Push Initiation

```
Core Engine
   │
   │  POST /mno/{network-id}/push  (PushCommand)
   ▼
Edge Server
   ├─ Check: virtual device registered for MSISDN?
   │
   ├─ YES → Generate sessionId
   │         Submit UssdRequest to Core Engine
   │         │
   │         │  HTTP POST /ussd  (UssdRequest)
   │         ▼
   │        Core Engine
   │         │
   │         │  HTTP 200 (UssdResponse)
   │         ▼
   │        Edge Server
   │         │  HTTP POST {callbackUrl}  (UssdResponse + sessionId + deviceId)
   │         ▼
   │        Virtual Device
   │         │  200 OK
   │         ▼
   │        Edge Server returns PushResult (sessionId) to Core Engine
   │
   └─ NO  → Plugin.InitiatePush(PushCommand)
            │
            │  MNO-specific push HTTP call
            ▼
           MNO Gateway
            │  sessionId
            ▼
           Edge Server returns PushResult (sessionId) to Core Engine
```

## Configuration

The edge-server is configured via a YAML configuration file. The path to this file is provided at startup via the `--config` flag or the `EDGER_CONFIG` environment variable.

```yaml
server:
  port: 8080
  simulation:
    enabled: true  # Set to false in production

coreEngine:
  url: "http://core-engine:8080"

plugins:
  directory: "/etc/edger/plugins"  # Directory from which .so files are loaded

  load:
    - file: "mno-a.so"                              # Filename within the plugins directory
      networkId: "mno-a"                            # Platform network identifier
      configFile: "/etc/edger/plugins/mno-a.yaml"  # Path to this plugin's config file

    - file: "mno-b.so"
      networkId: "mno-b"
      configFile: "/etc/edger/plugins/mno-b.yaml"

    # Same .so, different network contract (e.g. two operator agreements)
    - file: "mno-a.so"
      networkId: "mno-a-prepaid"
      configFile: "/etc/edger/plugins/mno-a-prepaid.yaml"
```

**Top-level fields:**

| Field | Description |
|---|---|
| `server.port` | HTTP port the edge-server listens on (default: `8080`) |
| `server.simulation.enabled` | Enables the Simulation API (recommended `false` in production) |
| `coreEngine.url` | Base URL of the core-engine |
| `plugins.directory` | Filesystem path from which plugin `.so` files are loaded. Files in this directory that are not listed under `plugins.load` are ignored. |
| `plugins.load` | List of plugin registrations (see below) |

**Per-plugin fields:**

| Field | Description |
|---|---|
| `file` | Filename of the compiled plugin `.so` within `plugins.directory` |
| `networkId` | Platform network identifier this plugin instance is bound to. Must be unique across all entries. |
| `configFile` | Path to the plugin's own configuration file, passed verbatim to the plugin's `Initialize` operation at startup |

The edge-server fails to start if:
- Any `networkId` is duplicated across plugin entries.
- Any plugin's `Initialize` operation returns an error (e.g. missing config file, invalid credentials).
- The core-engine URL is unreachable (optional startup probe, configurable).

## Observability

The edge-server emits metrics, traces, and structured logs aligned with the platform-wide observability standard.

### Metrics

Metrics are defined in the platform monitoring catalogue. The edge-server owns the following metric groups:

**Edge Server Metrics** — inbound traffic and push dispatch:

| Metric | Type | Key Dimensions |
|---|---|---|
| `edge_requests_received_total` | Counter | `network`, `short_code` |
| `edge_request_duration_seconds` | Histogram | `network` |
| `edge_request_errors_total` | Counter | `network`, `error_type` |
| `edge_push_sent_total` | Counter | `network` |
| `edge_push_errors_total` | Counter | `network`, `error_type` |
| `edge_push_duration_seconds` | Histogram | `network` |

The `error_type` dimension on `edge_request_errors_total` must distinguish between: `auth_failure`, `parse_error`, `plugin_not_found`, `core_engine_error`.

### Distributed Tracing

Plugins are responsible for starting a trace span when an inbound request arrives and propagating trace context through the `UssdRequest` to the edge-server. The edge-server propagates that context to the core-engine via standard HTTP headers (W3C `traceparent`). For push dispatch, the edge-server starts a span on the USSD Send API call and propagates context into the plugin's `InitiatePush` call.

### Structured Logs

Every request log entry must include: `requestId`, `network`, `shortCode`, `msisdn` (masked to last 4 digits), `durationMs`, and `outcome` (`success` / `error`). Internal error details are logged at `ERROR` level but must never appear in MNO-facing responses.

## Deployment Notes

**Horizontal scaling.** Because the edge-server is stateless, multiple instances can run behind a load balancer with no coordination required.

**Network placement.** Plugin HTTP servers are the only platform components that need to be reachable from MNO gateways. The edge-server itself and the core-engine must be on a private network segment not accessible from outside. Access restrictions for the USSD Send API and each plugin's listening port are handled at the infrastructure level.

**TLS termination.** Each plugin is responsible for its own TLS and authentication. Plugins that require mTLS or shared-secret authentication implement that within their own HTTP server. The edge-server itself only needs to be reachable internally.

**Health check.** The edge-server must expose:

```
GET /health
```

Returning HTTP `200` with a JSON body indicating the status of the core-engine connectivity and each registered plugin. Plugin status reflects whether the plugin's `Start` completed successfully and, for plugins with `SendsPush`, whether the push gateway was reachable on the last probe.

```json
{
  "status": "ok",
  "coreEngine": "ok",
  "plugins": {
    "mno-a": "ok",
    "mno-b": "degraded"
  }
}
```

A `degraded` plugin status means the plugin started successfully and is receiving inbound traffic, but its push gateway was unreachable on the last health probe. Only push dispatch for that network is impacted.
