# Core Engine

## Overview

The **core-engine** is the operational heart of the cardinal-stack. Where the edge-server's concern is protocol translation — converting MNO-specific wire formats to and from the platform's internal representation — the core-engine is where all business logic lives. It enforces multi-tenancy, owns the session lifecycle, drives backend dispatching, applies caching and template processing, protects subscriber privacy, and produces the telemetry that makes the platform observable.

The edge-server knows nothing about tenants, applications, or entry points. The core-engine knows nothing about MNO wire formats. The boundary between them is a single, well-defined HTTP interface: the edge-server posts a normalized `UssdRequest` and receives a `UssdResponse`.

The core-engine is implemented in **Go**.

---

## Responsibilities

The core-engine sits between the edge-server and the USSD application backends, orchestrating every interaction that passes through the platform. It is the sole component that understands tenants, spaces, applications, entry points, and sessions. The edge-server hands it a normalized request; the core-engine takes over from there — resolving which application should handle it, managing the session, driving the conversation with the backend, and composing the response that travels back through the edge-server to the subscriber.

All platform intelligence lives here: access control, session state, caching, privacy protection, push initiation, and the event stream. Neither the edge-server nor the application backends need to concern themselves with these concerns; the core-engine owns them entirely.

---

## Functionalities

- **Multi-tenancy** — manages Spaces, Networks, and Short Codes; enforces Space entitlements so that traffic for a given short code or network is only processed by applications that have been granted access to it.
- **Entry point resolution** — parses the dialed USSD code to identify the matching Dial entry point (short code matching, prefix and parameter parsing); checks for active suspensions and returns the configured suspension message when one is in effect.
- **Short-list enforcement** — when an entry point or backend has an associated short list, verifies that the requesting MSISDN is present; returns the exclusion message when it is not.
- **Session lifecycle management** — creates sessions on first contact, tracks status transitions (Active → Completed / Cancelled / Crashed / Expired / Terminated), and deletes session records on terminal status to protect subscriber privacy.
- **Backend dispatching** — resolves the application map (from cache or a fresh fetch), selects the appropriate backend when multiple backends are configured, drives the Get Initial Content / Process User Input loop, evaluates input traps, and handles the redirect protocol.
- **Caching** — caches activity content per activity + scope + variation key, and the application map per application; respects per-activity `maxAge` and `scope` settings.
- **Template processing** — detects when backend content is flagged as a Handlebars template and renders it against the current session values before delivery; the unrendered template (not the rendered output) is what gets cached.
- **Content trimming** — enforces the platform content length limit by truncating output at the last displayable character within the configured limit.
- **USSD redirects** — handles internal redirects (entry-point and activity level) and gateway redirects; enforces a configurable depth limit and rejects same-destination loops immediately.
- **Session resuming** — on the first Get Initial Content of a new session, informs the backend whether the previous session is resumable; loads all values from the previous session when the backend opts in.
- **USSD Push orchestration** — authenticates Push API callers via certificate CN verification, initializes the session from Push entry point defaults and the caller's payload, then delegates outbound delivery to the edge-server USSD Send API.
- **Privacy protection** — encrypts all session values at rest; deletes the session record when the session reaches a terminal status.
- **Event production** — emits structured events (session started/ended/resumed, request processed, errors, push initiated) to the event dispatcher.
- **Application interaction Telemetry** — exposes Prometheus metrics and propagates distributed trace context regarding the application interactions.

---

## Design Principles

**Pluggable persistence.** The session store and the cache are defined as interfaces. PostgreSQL and Valkey are the first-class implementations, but neither is hardwired into the core-engine. A deployment may substitute alternative implementations without changing application code.

**Stateless request processing.** No in-process state is carried between requests. All session state lives in the external store and cache. Any core-engine instance can handle any request for any session; there is no affinity requirement. This keeps failure domains small and makes horizontal scaling straightforward.

**Fail-fast on configuration errors.** If the store is unreachable, the cache is unreachable, a TLS certificate is missing or invalid, or a required configuration field is absent, the core-engine refuses to start. Invalid configuration is never silently tolerated.

**Privacy-by-design.** Session values are encrypted at rest using the configured key pair. When a session reaches a terminal status (Completed, Cancelled, Crashed, Expired, or Terminated) the session record is deleted from the store rather than retained. No subscriber data outlives the session that produced it.

## Technology Stack

| Technology | Role | Rationale |
|---|---|---|
| **Go** | Implementation language | Consistency with the edge-server; strong concurrency primitives; low-overhead HTTP server; single-binary deployment. |
| **PostgreSQL** | Primary data store | The relational model fits the configuration domain (spaces, networks, short codes, applications, entry points, backends, key pairs, short lists). Transactional guarantees are essential for correct entitlement checks and session writes. PostgreSQL is the first-class store implementation; the interface is pluggable for deployments that require an alternative. |
| **Valkey** | Cache | Low-latency key-value store used to cache activity content and the application map. Pattern-based key deletion supports efficient cache invalidation. Valkey is the first-class cache implementation; the interface is pluggable. |

## Exposed APIs

### Inbound USSD API

Consumed by the edge-server. Every inbound USSD request, whether originating from a real MNO gateway or from the Simulation API, arrives here.

```
POST /ussd
```

**Authentication:** mTLS. The edge-server presents a client certificate; the core-engine verifies it against the configured CA.

**Request body:**

```json
{
  "requestId": "uuid",
  "sessionId": "mno-assigned-session-id",
  "network": "mno-a",
  "msisdn": "+2547XXXXXXXX",
  "code": "*123*01*1000#",
  "input": "1",
  "location": {
    "mcc": "639",
    "mnc": "02",
    "lac": "1234",
    "cid": "56789"
  }
}
```

| Field | Type | Description |
|---|---|---|
| `requestId` | string (UUID) | Unique identifier assigned by the edge-server for this request |
| `sessionId` | string | Session identifier as provided by the MNO gateway |
| `network` | string | Platform network identifier (e.g. `mno-a`) |
| `msisdn` | string | MSISDN of the end user |
| `code` | string | (optional) Full USSD code dialed, including short code and parameters (e.g. `*123*01*1000#`) |
| `input` | string | (optional) User input string |
| `location.mcc` | string | (optional) Mobile Country Code |
| `location.mnc` | string | (optional) Mobile Network Code |
| `location.lac` | string | (optional) Location Area Code |
| `location.cid` | string | (optional) Cell ID |

**Response body (`200 OK`):**

```json
{
  "content": "Welcome\n1. Check balance\n2. Transfer funds",
  "requireInput": true
}
```

| Field | Type | Description |
|---|---|---|
| `content` | string | Screen content to display to the user |
| `requireInput` | boolean | `true` if the session is awaiting input; `false` if the session has terminated |

**Responses:**

| Status | Meaning |
|---|---|
| `200 OK` | Request processed; response body contains the USSD screen |
| `400 Bad Request` | Missing or invalid fields |
| `401 Unauthorized` | mTLS client certificate verification failed |
| `500 Internal Server Error` | Unrecoverable processing error |

### USSD Push API

Consumed by USSD applications to trigger a Push session toward a subscriber.

```
POST /spaces/{spaceId}/push/{entryPointId}
```

The `spaceId` and `entryPointId` path segments identify the target tenant and the exact Push entry point within it. This makes multi-tenancy explicit at the URL level: a caller can only trigger a push against an entry point in a space they have been authorized to access.

**Authentication:** mTLS using a certificate issued by the Certificate Issuer defined on the addressed Push entry point. The common name (CN) of the presented certificate must be listed in the authorized CNs configured on that entry point. Requests whose CN is not in the authorized list are rejected with `403 Forbidden`. Because authorization is entry-point-scoped, a certificate authorized for one entry point in a space grants no access to any other entry point, even within the same space.

**Request body:**

```json
{
  "network": "mno-a",
  "msisdn": "+2547XXXXXXXX",
  "sessionValues": {
    "transferAmount": "1000",
    "targetAccount": "254700000000"
  },
  "correlationId": "uuid"
}
```

| Field | Type | Description |
|---|---|---|
| `network` | string | Target network identifier |
| `msisdn` | string | MSISDN of the target subscriber |
| `sessionValues` | map[string]string | (optional) Key-value pairs to pre-populate in the session |
| `correlationId` | string | Identifier propagated for end-to-end tracing |

`entryPointId` and `spaceId` are taken from the path and must not be repeated in the body. The core-engine resolves the entry point within the specified space, validates the network entitlement for that space, initializes the session (merging Push entry point defaults with the supplied `sessionValues`), then calls the edge-server USSD Send API (`POST /mno/{network-id}/push`) to trigger delivery. The MNO session ID returned by the edge-server is stored against the session for correlation with subsequent inbound requests.

**Response body (`202 Accepted`):**

```json
{
  "sessionId": "mno-assigned-session-id"
}
```

| Field | Type | Description |
|---|---|---|
| `sessionId` | string | Session identifier assigned by the MNO gateway, as returned by the edge-server |

**Responses:**

| Status | Meaning |
|---|---|
| `202 Accepted` | Push accepted; response contains the MNO session ID |
| `400 Bad Request` | Missing or invalid fields |
| `401 Unauthorized` | mTLS verification failed |
| `403 Forbidden` | Certificate CN not in the authorized list for this entry point |
| `404 Not Found` | Space or entry point not found |
| `422 Unprocessable Entity` | The space does not have a network entitlement for the specified network, or the network entitlement does not permit push |
| `502 Bad Gateway` | Edge-server or MNO gateway returned an error |

### Administration API

The Administration API provides the full management surface for all objects tracked by the core-engine. It is grouped by domain:

**Networks & Short Codes**
Create, update, and delete Network records. Bind short codes to one or more networks. List and inspect existing networks and short codes.

**Spaces & Entitlements**
Create and manage Spaces. Assign and revoke short code entitlements and network entitlements (including push permission) for each space.

**Key Pairs & Certificate Issuers**
Create and rotate asymmetric key pairs within a space. Register Certificate Issuers (CA certificates) that the platform trusts for authenticating application callers.

**Applications, Backends, and Entry Points**
Create and configure Applications within a space. Register Backend services (HTTP URL, key pair selection, optional short list). Create and update Dial entry points (short code, prefix, parameters, suspension, short list, initial activity, caching, location) and Push entry points (Certificate Issuer, authorized CNs, default session values). Manage entry point suspensions.

**Short Lists**
Create and manage Short Lists within a space. Add and remove MSISDNs. Associate short lists with entry points or backends.

**Response Templates & Error Scenario Mappings**
Create and manage Response Templates within a space — each template is associated with a configured language slug and contains Handlebars content. Map error scenarios to templates (one template per language per scenario) within the space, overriding the global mappings defined in the configuration file for applicable scenarios.

**Activity Map Cache Invalidation**
Trigger invalidation of the cached application map for a specific application, forcing the next request to re-fetch from the backend.

---

### Operations API

The Operations API supports live troubleshooting and session assistance:

- **List active sessions** — query running sessions by network, short code, MSISDN, or application.
- **Inspect a session** — retrieve the current state, status, and crash reason (if applicable) for a specific session. Session values are never exposed — they remain encrypted at rest and are not accessible through the Operations API.
- **Stream a session** — receive a live stream of USSD content for a session as it progresses, enabling operators to see exactly what the subscriber sees.
- **Terminate a session** — force a session into the Terminated status; triggers session deletion and event emission.
- **Manage short lists at runtime** — add or remove MSISDNs from a short list without a full administration cycle; changes take effect immediately on the next request that consults the list.

## Core Processing Pipeline

### Inbound USSD Request (Dial Flow)

```
Edge Server
   │
   │  POST /ussd  (UssdRequest)
   ▼
Core Engine — Validate request
   │
   ├─ Resolve entry point
   │   ├─ Parse short code from UssdRequest.code
   │   ├─ Match short code to Space entitlement
   │   ├─ Match dial format (prefix + parameters) to entry point
   │   └─ Entry point NOT found → return "entry point not found" content
   │
   ├─ Suspension check
   │   └─ Active suspension → return suspension message
   │
   ├─ Short-list check (entry point level)
   │   └─ MSISDN NOT in list → return exclusion message
   │
   ├─ Session initialization / resuming
   │   ├─ New session: create session record
   │   ├─ Apply entry point default session values
   │   └─ Apply dial code parameter values mapped to session keys
   │
   └─ Backend dispatching
       │
       ├─ Resolve application map
       │   ├─ Cache hit → use cached map
       │   └─ Cache miss → GET application map from backend → cache it
       │       └─ Fetch failure → return internal error content
       │
       ├─ Backend selection (when entry point has two backends)
       │   ├─ Check short-list-gated backend first
       │   ├─ MSISDN in short list → use gated backend
       │   └─ MSISDN not in list → use ungated backend
       │
       ├─ Get Initial Content (first request for this activity)
       │   ├─ Cache hit (activity content, caching enabled on entry point)
       │   │   └─ isTemplate=true → render Handlebars template against session values
       │   └─ Cache miss → POST Get Initial Content to backend
       │       ├─ resumeSession=true in response and previous session resumable?
       │       │   └─ Load all values from previous session; set resumed=true
       │       ├─ Cache activity content if caching enabled
       │       ├─ Apply returned sessionUpdates to session
       │       ├─ isTemplate=true → render Handlebars template
       │       └─ HTTP 307 redirect? → handle redirect (see below)
       │
       ├─ Content trimming → truncate at configured character limit
       │
       ├─ requiresInput=false → terminal response; delete session record
       │
       └─ requiresInput=true → persist updated session; return UssdResponse
           │
           ▼
         [User provides input on next inbound request]
           │
           ├─ Input trap evaluation
           │   ├─ Input matches trap → issue Get Initial Content for trap target activity
           │   └─ No trap match → Process User Input
           │
           ├─ Process User Input → POST Process User Input to backend
           │   ├─ nextActivityId returned → issue Get Initial Content for that activity
           │   └─ content returned → trim → return UssdResponse
           │
           └─ HTTP 307 redirect? → handle redirect (depth limit: redirects.depthLimit; same-dest → crash)
   │
   │  HTTP 200 (UssdResponse)
   ▼
Edge Server
```

**Redirect handling:**

```
HTTP 307 from backend
   │
   ├─ Redirect-Type: EntryPoint
   │   └─ Re-resolve entry point by ID; restart dispatch from session init
   │
   ├─ Redirect-Type: Activity
   │   └─ Issue Get Initial Content for target activity; continue dispatch loop
   │
   └─ Redirect-Type: Gateway
       └─ Forward short code to edge-server gateway redirect endpoint;
          relay response to user
```

### Push Session Pipeline

```
USSD Application
   │
   │  POST /push  (entryPointId, network, msisdn, sessionValues, correlationId)
   ▼
Core Engine — Authenticate
   ├─ Verify client certificate against Push entry point's Certificate Issuer
   ├─ Check certificate CN against authorized CNs on entry point
   └─ Reject with 403 if CN not authorized
   │
   ▼
Resolve Push entry point
   ├─ Look up entry point by entryPointId
   └─ Verify network entitlement includes push permission
   │
   ▼
Initialize session
   ├─ Create session record (type=push)
   ├─ Apply entry point default session values
   └─ Merge caller-supplied sessionValues (caller values override defaults)
   │
   ▼
POST /mno/{network-id}/push  →  Edge Server  →  MNO Gateway
   │
   │  202 Accepted  {sessionId: "mno-assigned-id"}
   ▼
Core Engine
   ├─ Store MNO session ID against internal session for correlation
   └─ Emit push.initiated event
   │
   │  202 Accepted  {sessionId: "mno-assigned-id"}
   ▼
USSD Application

[Subscriber receives push; first inbound dial request arrives at edge-server]
   │
   │  POST /ussd  (sessionId=mno-assigned-id, sessionType=push)
   ▼
Core Engine — correlate by MNO session ID → resume session → backend dispatching
```

## Backend Contract

### Application Map

The application map is the full descriptor of a USSD application returned by the backend. Beyond the activity registry it carries application-level settings that apply across all activities. The core-engine fetches it from the backend and caches it per application.

**Fetch:** `GET {backendUrl}/application-map`

```json
{
  "defaultActivity": "main",
  "languageKey": "lang",
  "defaultLanguage": "en",
  "activities": {
    "main": {
      "contextKeys": ["user.msisdn", "session.network"],
      "sensitiveInput": false,
      "caching": {
        "enabled": true,
        "maxAge": 300,
        "scope": "global",
        "variationKey": ""
      }
    },
    "transfer": {
      "contextKeys": ["user.msisdn", "transferAmount", "targetAccount"],
      "sensitiveInput": false,
      "caching": {
        "enabled": true,
        "maxAge": 60,
        "scope": "user",
        "variationKey": "lang"
      }
    },
    "enter-pin": {
      "contextKeys": ["user.msisdn"],
      "sensitiveInput": true,
      "caching": {
        "enabled": false
      }
    }
  }
}
```

**Top-level fields:**

| Field | Type | Description |
|---|---|---|
| `defaultActivity` | string | ID of the activity the core-engine addresses when no initial activity is defined on the entry point. Typically `"main"`. Required — the backend must always declare this. |
| `languageKey` | string | (optional) Session key that holds the subscriber's language slug. When present, the core-engine reads this key from the session to select the correct language variant of the Response Template to render for any error scenario. If the key is absent from the session or its value does not match a configured language slug, the core-engine falls back to `defaultLanguage`. |
| `defaultLanguage` | string | (optional) Language slug to use when `languageKey` is not set, is absent from the session, or resolves to an unknown language slug. Must match a slug defined in the platform language configuration. When omitted, the core-engine uses the first language defined in the platform configuration as the fallback. |
| `activities` | object | Map of activity ID → activity descriptor. All activities the application exposes must be declared here. |

**Per-activity fields (`activities.*`):**

| Field | Type | Description |
|---|---|---|
| `contextKeys` | string array | Session keys whose values will be passed to the backend when this activity is requested |
| `sensitiveInput` | boolean | When `true`, the user input collected for this activity is treated as sensitive (e.g. a PIN or password). The core-engine must not log or store this input in plaintext and must instruct the MNO gateway to mask the input on the handset where the protocol supports it. |
| `caching.enabled` | boolean | Whether content caching is enabled for this activity |
| `caching.maxAge` | integer | Cache TTL in seconds. Required when `caching.enabled` is `true`. |
| `caching.scope` | enum | `global` — one cache entry shared across all users; `user` — one cache entry per MSISDN |
| `caching.variationKey` | string | (optional) Session key whose value is appended to the cache key to produce separate cache entries per variation (e.g. set to the language session key to cache content per language). |

The application map is cached in Valkey per application. Cache invalidation is available via the Administration API.

### Get Initial Content

Sent by the core-engine to retrieve the content for a specific activity.

**Request:** `POST {backendUrl}/activity/initialContent`

```json
{
  "activityId": "main",
  "application": {
    "id": "app-uuid",
    "entrypoint": {
      "id": "entry-point-id"
    }
  },
  "user": {
    "input": "*123*01*1000#",
    "msisdn": "+2547XXXXXXXX"
  },
  "session": {
    "network": "mno-a",
    "type": "dial",
    "id": "session-uuid"
  },
  "request": {
    "id": "request-uuid"
  },
  "context": {
    "transferAmount": "1000",
    "targetAccount": "254700000000"
  },
  "resumable": true
}
```

| Field | Description |
|---|---|
| `activityId` | ID of the activity whose initial content is being requested |
| `application.id` | Unique ID of the application in the platform |
| `application.entrypoint.id` | ID of the entry point that initiated this session |
| `user.input` | The USSD code dialed by the user |
| `user.msisdn` | MSISDN of the subscriber |
| `session.network` | Platform network identifier |
| `session.type` | `dial` or `push` |
| `session.id` | Unique session identifier |
| `request.id` | Unique request identifier |
| `context` | Map of session values corresponding to the activity's `contextKeys` |
| `resumable` | `true` if a previous session exists and falls within the 120-second resuming window |

**Response:**

```json
{
  "content": "Welcome {{user.msisdn}}\n1. Transfer\n2. Balance",
  "requiresInput": true,
  "sessionUpdates": {
    "lang": "en"
  },
  "inputTraps": [
    { "exact": "1", "activityId": "transfer" },
    { "exact": "2", "activityId": "balance" },
    { "pattern": "^[3-9]$", "activityId": "other-options" }
  ],
  "isTemplate": true,
  "resumeSession": false
}
```

| Field | Description |
|---|---|
| `content` | Screen content (or Handlebars template if `isTemplate=true`) |
| `requiresInput` | `true` if the screen expects input; `false` if the session ends here |
| `sessionUpdates` | (optional) Key-value pairs to write into the session |
| `inputTraps` | (optional) Ordered array of trap entries evaluated against the user's input. Each entry must declare exactly one of `exact` or `pattern`, plus an `activityId`. `exact` specifies a value that must match the input character-for-character. `pattern` specifies a RE2 regular expression. The core-engine tests traps in declaration order and takes the first match. When no trap matches, the core-engine falls through to a Process User Input request. An entry that declares both `exact` and `pattern`, or neither, is a contract violation and the core-engine must reject the application map. |
| `isTemplate` | `true` if `content` is a Handlebars template to be rendered by the platform |
| `resumeSession` | `true` if the platform should load all values from the previous session |

### Process User Input

Sent by the core-engine to deliver user input to the current activity for processing.

**Request:** `POST {backendUrl}/activity/input`

```json
{
  "activityId": "transfer",
  "application": {
    "id": "app-uuid",
    "entrypoint": { "id": "entry-point-id" }
  },
  "user": {
    "input": "1",
    "msisdn": "+2547XXXXXXXX"
  },
  "session": {
    "network": "mno-a",
    "type": "dial",
    "id": "session-uuid"
  },
  "request": { "id": "request-uuid" },
  "context": {
    "transferAmount": "1000"
  }
}
```

**Response — content path:**

```json
{
  "content": "Transfer confirmed.",
  "sessionUpdates": {
    "lastTransferAmount": "1000"
  }
}
```

**Response — next activity path:**

```json
{
  "nextActivityId": "confirm-transfer",
  "sessionUpdates": {
    "transferAmount": "1000"
  }
}
```

| Field | Description |
|---|---|
| `content` | Screen content to display (mutually exclusive with `nextActivityId`) |
| `nextActivityId` | ID of the next activity to navigate to (mutually exclusive with `content`) |
| `sessionUpdates` | (optional) Key-value pairs to write into the session |

**Rule:** `nextActivityId` and `content` are mutually exclusive. `nextActivityId` must differ from the `activityId` supplied in the request; if it is the same, the platform returns an error to the user and crashes the session.

### Redirect Protocol

The backend signals a redirect by returning HTTP `307 Temporary Redirect` with custom headers. The `Location` header is always `/`. The redirect type is determined by the `Redirect-Type` header.

**Entry-point redirect** — re-enter the platform at a different entry point:

```
HTTP/1.1 307 Temporary Redirect
Location: /
Redirect-Type: EntryPoint
Entry-point: {entry-point-id}
```

**Activity redirect** — jump to a different activity within the current application:

```
HTTP/1.1 307 Temporary Redirect
Location: /
Redirect-Type: Activity
Activity: {activity-id}
```

**Gateway redirect** — exit the platform and redirect the subscriber to an external USSD application via the MNO gateway:

```
HTTP/1.1 307 Temporary Redirect
Location: /
Redirect-Type: Gateway
Short-Code: {short-code}
```

**Constraints:**

- The redirect depth limit is controlled by `redirects.depthLimit` in configuration (default: `3`). Reaching the limit returns an error to the user and crashes the session.
- Redirecting to the same destination as the current request (same entry point or same activity) is not permitted and causes an immediate session crash.

---

### Session Resuming

On the **first** Get Initial Content request of a new session, the platform includes `"resumable": true` if a previous session for the same MSISDN and entry point exists and its last update was within the past **120 seconds** and its status is one of: `Cancelled`, `Active`, `Crashed`, or `Expired`.

If the backend responds with `"resumeSession": true`, the platform:

1. Loads **all session values** from the previous session into the current session.
2. Sets `"resumed": true` as a session value, making it available to the backend as context on all subsequent requests.

Sessions with a `Completed` or `Terminated` status, or with a last update older than 120 seconds, are not resumable. The 120-second window is measured from the `updatedAt` timestamp on the previous session record.

---

### Error Handling and Session Crashes

When the core-engine encounters an error it cannot recover from during the processing of a USSD request, it:

1. **Transitions the session to `Crashed`** — the session status is updated to `Crashed` in the store.
2. **Records a crash reason** — a structured `crashReason` is written to the session record to facilitate troubleshooting. The crash reason identifies the error scenario and, where available, includes contextual detail such as the activity ID being processed and the HTTP status returned by the backend.
3. **Renders and returns a Response Template** — the core-engine resolves the Response Template mapped to the error scenario (see [Response Templates](#response-templates)), selects the correct language variant using the session's language key, renders it through the Handlebars template engine, and returns the result to the subscriber. This ensures the subscriber always sees a controlled, operator-defined message rather than an internal error detail.

The error scenarios that can occur during session processing are:

| Scenario key | When it is triggered |
|---|---|
| `internalError` | An unexpected platform-level failure (e.g. store unreachable, unhandled panic) |
| `backendInternalError` | The backend returned an unexpected HTTP status or a malformed response |
| `backendViolation` | The backend violated the USSD flow — same-destination redirect, `nextActivityId` equal to current activity, or redirect depth limit exceeded |
| `suspendedEntryPoint` | The matched entry point has an active suspension |
| `incorrectCodeFormat` | The dialed code matched a short code but did not match any entry point's dial format |

**Crash reasons** written to the session record use the scenario keys from the table above, extended with contextual fields:

```json
{
  "reason": "backendViolation",
  "activityId": "transfer",
  "detail": "nextActivityId equals current activityId"
}
```

| Field | Description |
|---|---|
| `reason` | Error scenario key (see table above) |
| `activityId` | (optional) Activity being processed at the time of the crash |
| `detail` | (optional) Additional context — HTTP status, constraint violated, or failure description |

Crash reasons are accessible via the Operations API and are included in the `session.error` event emitted to the event dispatcher. They are never surfaced to the subscriber.

## Response Templates

Response Templates are operator-defined content rendered by the core-engine to communicate error scenarios to subscribers. They replace any notion of hardcoded error strings — every subscriber-facing error message is the rendered output of a template.

### Languages

Languages are defined globally in the core-engine configuration file. Each language has a **slug** (the identifier used in session values and template associations) and a **name** (for display purposes).

```yaml
languages:
  - slug: en
    name: English
  - slug: sw
    name: Swahili
  - slug: fr
    name: French
```

All Response Template definitions — both global and space-level — must reference a slug from this list. The core-engine refuses to start if a template references an unknown language slug.

### Template Structure

A Response Template has:

| Field | Description |
|---|---|
| `id` | Unique identifier for the template |
| `language` | Language slug this template is written in — must match a configured language |
| `content` | Handlebars template string rendered by the core-engine before delivery to the subscriber |

Templates are pre-processed using the Handlebars template engine at render time. The following variables are available during rendering:

| Variable | Description |
|---|---|
| `{{session.id}}` | Current session identifier |
| `{{session.network}}` | Network identifier |
| `{{application.id}}` | Application identifier |
| `{{entrypoint.id}}` | Entry point identifier |

A single template may be mapped to more than one error scenario.

### Error Scenarios

Each error scenario can be mapped to one Response Template per configured language. When a scenario is triggered, the core-engine selects the template for the language resolved from the session (via `languageKey` and `defaultLanguage` in the application map), renders it, and returns the result to the subscriber.

**Space-level scenarios** — mappable per Space/Tenant via the Administration API:

| Scenario key | When it is triggered |
|---|---|
| `suspendedEntryPoint` | The matched entry point has an active suspension |
| `backendInternalError` | The backend returned an unexpected HTTP status or malformed response |
| `backendViolation` | The backend violated the USSD flow (same-destination redirect, `nextActivityId` = current activity, redirect depth exceeded) |
| `internalError` | An unexpected platform-level failure |
| `incorrectCodeFormat` | The dialed code matched a short code but did not match any entry point's dial format |

**Global scenarios** — mappable only in the core-engine configuration file:

| Scenario key | When it is triggered |
|---|---|
| `unknownShortCode` | The dialed code did not match any known short code |
| `suspendedEntryPoint` | Active suspension — global fallback when no space-level mapping is defined |
| `backendInternalError` | Backend error — global fallback |
| `backendViolation` | Backend violation — global fallback |
| `internalError` | Platform-level failure — global fallback |

### Resolution Order

When an error scenario is triggered, the core-engine resolves the template as follows:

1. Look up the space-level mapping for the scenario. If a template is mapped for the resolved language, render and return it.
2. If no space-level mapping exists for the scenario and language, fall back to the global mapping for the same scenario and language.
3. If neither mapping exists, render the content of the matching global template for the `defaultLanguage`.
4. If no global mapping exists at all for the scenario, return a hardcoded platform default string.

Space-level mappings always take precedence over global mappings for applicable scenarios. Scenarios that are only defined at the global level (`unknownShortCode`) cannot be overridden at space level.

## Session Store

**What is persisted:** One session record per active session, including all session values encrypted using the space's configured key pair.

**Write lifecycle:**

- **Created** — on first request for a new session; record is written with status `Active`.
- **Updated** — after each request that does not terminate the session; `values` and `updatedAt` are rewritten; status may transition (e.g. to `Cancelled` on user hang-up signaled by the MNO).
- **Deleted** — immediately when the session reaches a terminal status (`Completed`, `Cancelled`, `Crashed`, `Expired`, `Terminated`). Deletion is permanent; no archive copy is retained.

**Encryption:** All session values are encrypted before writing to the store using the key pair associated with the application's space. Raw values are never written in plaintext.

**TTL-based expiry:** The store implementation must support TTL-based automatic expiry of session records to handle abandoned sessions that never receive an explicit terminal signal from the MNO. The TTL is set on each write and reset on each update.

**Pluggable store interface — required operations:**

| Operation | Description |
|---|---|
| `Create(session)` | Persist a new session record |
| `Get(sessionId)` | Retrieve a session record by ID |
| `GetByMnoSessionId(mnoSessionId)` | Retrieve a session record by MNO-assigned session ID (for push correlation) |
| `Update(session)` | Overwrite an existing session record |
| `Delete(sessionId)` | Remove a session record permanently |
| `SetTTL(sessionId, ttl)` | Set or reset the expiry TTL on a session record |

## Cache

**What is cached:**

- **Activity content** — the raw response (content string, `isTemplate` flag, `inputTraps` map) from a Get Initial Content backend call, keyed by activity ID + scope dimension + variation key value.
- **Application map** — the full application map object, keyed by application ID.

**Cache key structure:**

```
activity:{applicationId}:{activityId}:global                           (global scope, no variation)
activity:{applicationId}:{activityId}:global:{variationValue}          (global scope, with variation)
activity:{applicationId}:{activityId}:user:{msisdn}                    (user scope, no variation)
activity:{applicationId}:{activityId}:user:{msisdn}:{variationValue}   (user scope, with variation)

appmap:{applicationId}
```

**TTL / maxAge:** Each activity cache entry uses the `maxAge` value from the activity's caching configuration in the application map. The application map cache entry uses a platform-wide default TTL configurable in the core-engine configuration.

**Scope semantics:**

- `global` — one entry for all users; shared across all sessions for that activity. Suitable for static or slowly-changing content.
- `user` — one entry per MSISDN; suitable for personalized content that varies by subscriber.

**Variation key:** When a `variationKey` is configured for an activity, the value of that session key is appended to the cache key. This produces separate cache entries for each distinct value — for example, separate entries per language when `variationKey` is `lang`.

**Cache invalidation:** The Administration API exposes an invalidation endpoint per application that deletes all cache entries matching `appmap:{applicationId}` and all `activity:{applicationId}:*` keys using pattern-based deletion.

**Pluggable cache interface — required operations:**

| Operation | Description |
|---|---|
| `Get(key)` | Retrieve a value by key; returns nil if absent or expired |
| `Set(key, value, ttl)` | Store a value with the given TTL |
| `Delete(key)` | Remove a specific key |
| `DeleteByPattern(pattern)` | Remove all keys matching a glob pattern (used for cache invalidation) |

## Security

**mTLS: edge-server → core-engine.** All traffic from the edge-server to the core-engine's Inbound USSD API is protected by mutual TLS. The edge-server presents a client certificate; the core-engine verifies it against its configured CA. Connections without a valid client certificate are rejected before any request processing begins.

**mTLS: core-engine → backend.** All traffic from the core-engine to application backends is protected by mutual TLS. The core-engine presents the key pair configured on the backend; backends are expected to verify the presented certificate.

**Key pair signing for backend requests.** Each backend defines a key pair. The core-engine signs backend requests using the private key of that pair, enabling backends to verify the authenticity of platform-originated calls.

**Certificate Issuer / CN verification for Push API callers.** Push entry points define a Certificate Issuer and a list of authorized certificate common names. The core-engine verifies the caller's certificate against the issuer and checks the CN against the authorized list before processing any push request.

**Short-list gating.** Entry points and backends may be gated by a short list. Requests from MSISDNs not in the list are rejected at the entry point level (with the exclusion message) or routed to the ungated backend before any backend call is made. Short-list checks add no backend round-trips.

**Session data encryption at rest.** All session values are encrypted before being written to the store. The encryption key is derived from the key pair associated with the session's application space. Decryption occurs only in-process during request handling; the store never holds plaintext values.

**Session record deletion on terminal status.** When a session ends for any reason, its record is deleted from the store. There is no soft-delete or archival path for session records. This is a hard privacy guarantee: subscriber data does not persist beyond the session that produced it.

### Distributed Tracing

Trace context is propagated using the W3C `traceparent` header throughout the request path:

- **Edge-server → core-engine:** The edge-server starts a trace span for each inbound request and propagates the trace context in the `traceparent` header on the `POST /ussd` call. The core-engine creates a child span under this context for all processing it performs.
- **Core-engine → backend:** The core-engine propagates the trace context to each backend call (Get Initial Content, Process User Input, application map fetch) via the `traceparent` header on the outbound HTTP request.

**Span naming conventions:**

| Operation | Span name |
|---|---|
| Inbound USSD request processing | `core_engine.ussd.process` |
| Application map fetch | `core_engine.appmap.fetch` |
| Get Initial Content call | `core_engine.backend.get_initial_content` |
| Process User Input call | `core_engine.backend.process_user_input` |
| Cache lookup | `core_engine.cache.get` |
| Cache write | `core_engine.cache.set` |
| Session store read | `core_engine.store.get` |
| Session store write | `core_engine.store.write` |
| Push initiation | `core_engine.push.initiate` |

## Deployment Notes

**Horizontal scaling.** The core-engine processes every request statelessly: all session data lives in the external store and all cached content lives in the external cache. Any number of core-engine instances can run behind a load balancer with no affinity requirement. Scale-out requires only that all instances share the same `store.dsn` and `cache.dsn`.

**Network placement.** The core-engine is an internal component. It must not be reachable from MNO gateways, the public internet, or any subscriber-facing network segment. The Inbound USSD API is consumed only by the edge-server; the Push API is consumed only by internal USSD application backends. Network-level access controls must enforce this placement.

**Health check.** The core-engine must expose:

```
GET /health
```

Returning HTTP `200` with a JSON body indicating the status of the store, cache, and event dispatcher connectivity:

```json
{
  "status": "ok",
  "store": "ok",
  "cache": "ok",
  "eventDispatcher": "ok"
}
```

If any dependency is unreachable, the corresponding field reflects `"degraded"` or `"unavailable"` and the top-level `"status"` field reflects the worst observed state. A `degraded` event dispatcher means events may be lost but USSD request processing continues. A `degraded` or `unavailable` store or cache means the core-engine cannot process requests and the health check returns HTTP `503`.
