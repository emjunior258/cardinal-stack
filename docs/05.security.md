# Security

## Access Management

Cardinal Stack implements a Role-Based Access Control (RBAC) model for the Administration and Operations APIs. The model is designed around three core principles:

- **Identity is owned by the Identity Provider.** The platform trusts JWTs issued by the configured IdP and never manages credentials.
- **Authorization is owned by the platform.** Role assignments are managed exclusively via the Administration API. The IdP has no knowledge of tenant or application-level roles.
- **Least privilege by design.** Roles are narrowly scoped. Configuration, operations, and access management are separated into distinct roles at every level.

### Principals

A principal is an entity to which a role can be assigned. The platform recognises three principal types, each identified by a claim in the JWT:

| Type | JWT Claim | Description |
|---|---|---|
| `user` | `sub` | A human user authenticated via Authorization Code flow |
| `group` | `groups` | An Identity Provider group. Matches any entry in the `groups` claim array |
| `client` | `client_id` | A machine-to-machine client authenticated via Client Credentials flow |

### Role Assignments

A role assignment is a record of the form `(principal, role, scope)`.

**Scopes** define the boundary within which a role is effective:

| Scope | Description |
|---|---|
| `platform` | Applies across the entire platform |
| `space(spaceId)` | Applies within a specific space |
| `application(spaceId, appId)` | Applies within a specific application |

**Conflict resolution:** When multiple assignments match the same principal within the same scope, the highest privilege role takes effect.

**Scope boundary:** A role assignment never grants access beyond its defined scope. A space-scoped assignment grants no visibility into sibling spaces. An application-scoped assignment grants no visibility into sibling applications within the same space.

### Root Access

Root is a special access level that bypasses all permission checks. It exists exclusively to bootstrap the platform — whoever holds Root assigns the first Platform Access Admin and Platform Configurator, then steps back.

Root is not a role that can be assigned via the Administration API. It is configured exclusively via the platform configuration file:

```yaml
security:
  access_management:
    root_access:
      subs:        ["..."]   # matched on `sub` claim
      groups:      ["..."]   # matched on `groups` claim
      client_ids:  ["..."]   # matched on `client_id` claim
```

Any combination of `subs`, `groups`, and `client_ids` may be specified. Multiple principals can hold Root simultaneously.

> **Warning:** The platform emits a startup warning if Root principals are configured when running in production mode. Root access should be removed from the configuration once the initial Platform Access Admin and Platform Configurator assignments have been made.

### Environment-Conditional Permissions

Certain permissions are restricted to non-production deployments. When the platform is running in production mode, Space Developers and Application Developers lose access to Debug Probes and Session Recordings regardless of their role assignment. This protects real subscriber data from being exposed to developers in production environments.

## Roles

Roles are organised into three levels that mirror the platform's resource hierarchy: platform, space, and application.

### Platform-Level Roles

Platform-level roles are assigned at platform scope and apply across the entire platform.

| Role | Description |
|---|---|
| **Platform Configurator** | Manages platform infrastructure: networks, short codes, spaces, space entitlements, and global response templates and error mappings. Has no access management privileges. |
| **Platform Access Admin** | Manages role assignments at platform scope and space scope. Has no resource configuration privileges. |
| **Platform Operator** | Troubleshoots issues across all spaces and applications. Has CRUD access to short lists and full access to the Operations API across all spaces. |
| **Platform Config Viewer** | Read-only access to all administration API resources across all spaces. No Operations API access. |

### Space-Level Roles

Space-level roles are assigned at space scope and apply within a specific space.

| Role | Description |
|---|---|
| **Space Configurator** | Full configuration control within the space: key pairs, certificate issuers, short lists, response templates, error mappings, applications, backends, entry points, and session tag rules. Has no access management privileges. |
| **Space Access Admin** | Manages role assignments within the space and its applications. Has no resource configuration privileges. |
| **Space Developer** | Manages applications and all application sub-resources within the space. Has no access to the Operations API. In non-production environments, can create debug probes and view session recordings. |
| **Space Operator** | Read-only access to all space configuration resources. Full Operations API access for the space including cache invalidation and runtime short list management. |
| **Space Viewer** | Read-only access to all space resources. |
| **Short List Manager** | Creates and manages short lists within the space. Manages short lists at runtime via the Operations API. Designed for delegation to non-engineering teams such as marketing or operations. |

### Application-Level Roles

Application-level roles are assigned at application scope and apply within a specific application. Application-level roles have no visibility into sibling applications within the same space.

| Role | Description |
|---|---|
| **Application Developer** | Full configuration of the application: backends, entry points, and session tag rules. Read access to space short lists for reference. Has no access to the Operations API. In non-production environments, can create debug probes and view session recordings. |
| **Application Operator** | Full Operations API access for the application. Read-only access to application configuration. |
| **Application Viewer** | Read-only access to application configuration and non-sensitive Operations API data. |

## Role Assignment Permissions

The ability to assign roles is itself governed by role. The table below defines which roles can assign which other roles and within which scope.

| Assignor | Assignable Roles | Scope |
|---|---|---|
| **Root** | Any role | Any scope |
| **Platform Access Admin** | Platform Access Admin, Platform Operator, Platform Config Viewer, Space Access Admin, Space Configurator, Space Developer, Space Operator, Space Viewer, Short List Manager, Application Developer, Application Operator, Application Viewer | Platform + all spaces + all applications |
| **Space Access Admin** | Space Access Admin, Space Configurator, Space Developer, Space Operator, Space Viewer, Short List Manager, Application Developer, Application Operator, Application Viewer | Own space + its applications |

**Key constraints:**

- Only Root can assign Platform Configurator
- Only Root can assign or revoke Root
- Platform Access Admin cannot assign Root or Platform Configurator
- Space Access Admin cannot assign any platform-level roles
- All assignments are strictly contained within the assignor's scope
